# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

This project is a web app called **FinanGold** (the app's display name — the `<title>`, login screen, and sidebar all show "FinanGold"), built from scratch for "Ipanema Joias" (the multi-store jewelry business whose data it manages: stores include Ipanema, Recreio, Ricardo Angra; companies include Dantas, GPHD, DHD). Don't conflate the two: "FinanGold" is the product name, "Ipanema Joias" is the customer/business the data belongs to. The current source of truth for data is a Google Sheets spreadsheet (a local copy exists at `Fluxo de caixa Ipanema Joias.xlsx` for reference/inspection only — the app talks to the live Google Sheet, not this file). `TESTE MD` is an empty placeholder, not example code. The project is a git repository, published (see Deployment) and in use — treat every change as going to real users once pushed.

### Spreadsheet structure (reference)

- **Lançamento** — the cash-flow ledger (thousands of rows). Columns: Data, Loja, Conta, Empresa, Categoria, Valor, Tipo (Entrada/Saída), Peso (g), Pessoa, Observação.
- **Estoque** — jewelry inventory. Columns: Produto, Tipo, Marca, Condição, Estado, Peso em grama, Pureza (k), Valor de Custo, Valor de venda, Data de Compra, Data de Venda, Comprador, Vendedor, Loja, Vendido?, Observação.
- Lookup/domain tabs (small, list-style — used as dropdown sources): **Pessoa, Contas, Categoria, Lojas, Produto, Tipo de Produto, Marcas, Empresas**. Each entry typically has a numeric code and a "código - nome" complement column used elsewhere as the display value.

## Tech stack

Plain HTML, CSS, and JavaScript only — no frameworks, bundlers, or npm build tooling. Google Sheets integration uses Google Identity Services (OAuth, user login in-browser) plus the Sheets API directly from client-side JS — no backend server. The user already has a Google Cloud OAuth Client ID configured. Development is tested over a local HTTP server (not `file://`, which breaks Google OAuth).

### Multi-company (multi-tenant) routing

The app supports managing several companies' spreadsheets from one login screen, routed by the signed-in Google account's email:

- `js/tenants.js` — `TENANTS`, a plain object mapping an email to an **array** of `{ empresa, spreadsheetId, sheetName }` profiles (one email can manage several companies). This is how "mccomb.matheus@gmail.com → Ipanema Joias → (that company's spreadsheet)" is wired up. To onboard a new company: share its spreadsheet (same tab/column layout as the existing one) with the relevant Google account(s) in Drive, then add/extend that email's entry here.
- **`selectCompanyAndLoadApp` loads Lançamentos, lookups, and Estoque independently** (`Promise.allSettled`, not `Promise.all`) — different companies' spreadsheets can have inconsistent tab structures (discovered when adding a second company whose sheet didn't fully match), so one tab being missing/misnamed degrades that one section instead of blanking the whole app. Failures are collected and shown together in `#status-message` with each underlying error's message, not a generic "something went wrong."
- **Display name + roles, gated by Master — no self-registration**: `js/usuarios.js` manages a `Usuários` tab (Email, Nome, Perfil) inside *each company's own spreadsheet* — not a global/shared directory, since there's no cross-company data store in this architecture. `ensureUsuariosSheet` creates that tab on first use, or upgrades a pre-existing 2-column version from before roles existed (`migrateUsuariosPerfilColumn` backfills any row with a blank `Perfil` to `Master`, since those users already had full access before roles existed — grandfathered in, not guessed).
  - **Access is allow-listed, not self-service.** `js/app.js`'s `resolveProfileAndEnter` looks up the signed-in email in that company's `Usuários` tab. Found → straight into the app as that person (`startApp`, using their stored `Nome`/`Perfil`). Not found *and the tab already has at least one person in it* → `showAcessoNegadoScreen` (`#acesso-negado-screen`), a dead end with only a "Sair" button — there is deliberately no way to grant yourself access. Not found *and the tab is completely empty* → `showCadastroScreen` (`#cadastro-screen`): this is a **one-time bootstrap exception**, since a brand-new company has no Master yet to have added anyone, and `registerUsuario`'s own logic (in `js/usuarios.js`) assigns `Master` only when the tab was empty, `Visualizador` otherwise — so this path can only ever produce the founding Master, never a random signup. Any error while checking access **fails closed** (shows "acesso não liberado" with the error appended, never lets someone in on a fetch failure).
  - **Roles are never displayed as a label anywhere in the app UI** — per explicit user instruction, the tiering stays invisible to end users; it only manifests as which nav items, sections, and buttons exist for them. The Master-only user-management UI lives inside **Ajustes** (see below), not as its own nav item, and is invisible to anyone but Master.
  - **`js/roles.js`** defines the three constants (`ROLE_VISUALIZADOR`/`ROLE_EDITOR`/`ROLE_MASTER`), the global `currentUserRole` (set once in `startApp`), and `canEdit(role)`/`isMaster(role)`. `canEdit` gates: the five "Novo/Nova ..." buttons on the listing screens (`applyRoleVisibility` in `js/nav.js`, called once per login — see the sidebar-simplification note further down for why these moved off the sidebar itself) and the Estoque action buttons (custody/return/sold — `renderEstoqueActions`'s early return in `js/estoque-ui.js`). `isMaster` gates the `#ajustes-usuarios-section` div inside the Ajustes view (add-user form + a per-row role `<select>` that writes immediately via `updateUsuarioPerfil`, in `js/usuarios-admin.js`).

### Ajustes (settings)

A single nav item, always visible (`data-view="ajustes"`, `#view-ajustes`), holding admin-adjacent cards — internal identifiers still say "ajustes" even though this could theoretically be styled/labeled differently later; keep code and label in sync if renamed again (see the earlier "Fluxo de Caixa" naming note for why this matters).

- **Minha conta** — name/email/company, populated in `startApp` (which now takes a `linha` argument too, tracked as `currentUserLinha` — the signed-in user's own row in `Usuários`, needed to write their edits back to the right place). An "Editar perfil" button (`setupEditarPerfilForm`) reveals an inline Nome + Tipo de perfil form: **Nome is editable by anyone** (`updateUsuarioNome`); **Tipo de perfil is always shown but only enabled for Master** (`tipoSelect.disabled = !isMaster(...)`) — explicit user requirement: the control must stay visible to everyone, never hidden, but a non-Master can't actually change it. The submit handler re-checks `isMaster` before ever calling `updateUsuarioPerfil`, so even a disabled-attribute bypass (e.g. via devtools) can't write a role change — the same UI-gate-not-security-boundary caveat as everywhere else in this feature, just layered twice here since the control is deliberately not hidden.
- **Trocar de empresa** (`#ajustes-trocar-empresa-card`, hidden unless `currentCompanies.length > 1`) — re-shows the company picker for the *same* token (`showCompanyPicker(currentCompanies, accessToken, currentEmail)`), reusing the exact same `resolveProfileAndEnter` path a fresh login would take (including its own access check against the target company's `Usuários` tab) — no separate "switch company" logic to keep in sync.
- **Atualizar dados lives only on the Dashboard now** — a small `.icon-btn` (`#btn-refresh-dashboard`) at the end of the filter row, not a card in Ajustes (removed after the user found the duplication redundant). On click, `refreshAllData()` (in `js/app.js`) disables the button and swaps its label to "Atualizando…" (plain text, no spin/rotation — an earlier CSS spin animation was deliberately removed as "too animated") while it re-fetches lançamentos, lookups, and estoque (reusing `refreshLancamentosAndDashboard`/`refreshEstoque` rather than duplicating their logic) without resetting any view's current filters, plus `refreshUsuariosAdmin()` if Master. Also keeps `estoqueLookups` (a module-level var in `js/estoque-ui.js`) in sync with freshly-fetched lookups — otherwise the custody/sold inline pickers would keep offering a stale `Pessoa` list after a refresh. Its click listener is still wired inside `setupAjustesHandlers` (despite the name) alongside "Trocar de empresa" and "Editar perfil" — that function is really "one-time setup for persistent post-login action buttons," not literally scoped to the Ajustes screen.
- **Editing and removing people (Master, in the same Usuários table)**: each row has **Editar** (name and e-mail become inputs → Salvar/Cancelar; `saveUsuarioEdit` in `js/usuarios-admin.js` validates the e-mail shape and rejects a duplicate) and **Remover** (two steps: the button turns into "Confirmar remoção"), plus the live role `<select>`. Removal blanks the row (`removeUsuario` in `js/usuarios.js`); the app and the gateway skip rows with no e-mail, and the gateway drops its 20 s Usuários cache on every write, so a removed person — or someone whose e-mail was changed — is locked out on their very next request. Guards: you cannot remove your own access, and the last Master can neither be removed nor demoted ("a empresa precisa ter pelo menos um Master") — that one is enforced in the UI only, so a Master editing the sheet by hand could still empty it. The gateway needed no change: a Master may already write anywhere on Usuários. The add form also refuses an invalid or already-listed e-mail.
- **`#ajustes-usuarios-section`** — the user/role management UI (moved here from a former standalone "Usuários" nav item), gated by `isMaster`.
  - **This is a UI-level gate for workflow, not a real security boundary** (same caveat as `TENANTS`): a Visualizador whose Google account happens to have Drive edit access to the spreadsheet could still write to it outside this app. The actual security boundary remains each spreadsheet's Drive sharing settings; this feature exists so people don't *accidentally* use capabilities they're not meant to, not to stop a determined bad actor.
- **One company → straight into the app; more than one → a picker screen** (`#company-picker-screen`, `showCompanyPicker` in `js/app.js`) lets the user choose which company to work in after login, before `#app-shell` ever becomes visible. `selectCompanyAndLoadApp` is the single place that applies a chosen tenant's `spreadsheetId`/`sheetName` onto `CONFIG` and kicks off the data load — both the auto-select (1 company) and manual-pick (2+) paths call it, so they can't drift apart.
- **This mapping is routing, not the real access control.** The actual security boundary is each spreadsheet's own Google Drive sharing settings — a user's OAuth token can only read/write a sheet if their Google account was separately given Drive access to it. An email present in `TENANTS` but never shared the spreadsheet will still get 403s from the Sheets API; an email absent from `TENANTS` just never gets routed anywhere by this app (harmless either way, since Drive is the real gate).
- `js/auth.js`'s `fetchUserEmail(token)` calls Google's `userinfo` endpoint, which needs the `.../auth/userinfo.email` scope — `CONFIG.SCOPES` in `js/config.js` now requests that alongside `.../auth/spreadsheets`. A session token from before this change won't have it; log out and back in if identity lookup fails.
- **Every sign-in verifies the token actually has every scope in `CONFIG.SCOPES`** (`getTokenScopes` + `hasAllScopes` in `js/auth.js`, checked first thing in `handleSignedIn`) — found necessary because a token can come back with only *some* requested scopes granted (e.g. the account owner unchecked one on Google's consent screen, or a stale session token predates a scope change), and that failure mode is otherwise invisible until every individual Sheets call starts throwing `403 ACCESS_TOKEN_SCOPE_INSUFFICIENT` with no clear cause. On a mismatch the session is cleared and the login screen shows one plain-language message instead of letting three separate fetches fail with cryptic API errors.
- `CONFIG.SPREADSHEET_ID` (and `CONFIG.SHEET_NAME`) are no longer fixed in `config.js` — they start empty and get set onto `CONFIG` at sign-in time in `js/app.js`'s `handleSignedIn`, once the tenant is resolved, *before* any data fetch happens. Every other file still just reads `CONFIG.SPREADSHEET_ID`/`CONFIG.SHEET_NAME` as before — this was a deliberately minimal-footprint change, not a rewrite of the data layer.
- If the signed-in email isn't in `TENANTS`, `handleSignedIn` clears the session token and shows an error on the login screen without ever revealing `#app-shell` — the app shell only becomes visible after a tenant is confirmed.
- The active company's name is shown under the "FinanGold" sidebar title (`#sidebar-empresa`), so a user managing multiple companies always knows which one they're in for that session. There's no in-app switcher to change company without logging out/back in yet — not requested so far, but `showCompanyPicker` already has everything needed if that's wanted later (just re-show it instead of routing straight to `selectCompanyAndLoadApp`).

### Visual design system

Went through **six** iterations with the user — history matters because the direction changed several times:
1. Sapphire blue + a muted gold secondary accent, gradients, glowing shadows — rejected ("não curti os tons").
2. One muted slate-blue accent (`#2c3e50`), flat and sober — rejected as too plain: the user wanted real typographic hierarchy, richer interaction and a "fintech/startup" feel (Nubank, BTG, XP, Apple, Samsung as references).
3. A light UI with a confident indigo accent (`#4f46e5`), light sidebar, soft shadows — approved, shipped, then rejected after launch: "o design não é bom, quero outros elementos, tirando a cor roxa" — wanting seriousness, power, positioning and something innovative, with Behance brand-identity references (near-black ground, neon accent, technical mono type, bento tiles, isometric wireframes and halftone dot-matrix art).
4. "Ouro" — near-black graphite ground, one gold accent, mono technical labels, bento layout, wireframe/halftone art. Prototyped first as a Design-canvas Artifact with two directions (electric-green-turned-deep-blue, and gold); the user picked gold ("utilize as cores do amarelo direção b"). Lived from 2026-09 to 2026-10-12, then replaced outright (not refined) by iteration 5 below, for a reason outside the app itself: the user incorporated a real company, **Finan. Capital**, to run this product, with its own already-finished brand (navy/gold/off-white, Sora, a "F." mark) — adopting it was not optional the way earlier redesigns were a matter of taste.
5. **"Finan. Capital"** (2026-10-12, superseded 2026-10-15 by iteration 6 below — kept for context, not current) — off-white ground (not dark), navy (`#0b1f3a`) as a second structural color (sidebar, the auth screen's brand panel), one gold accent (`#c99a2e`), Sora as the only typeface (replacing Space Grotesk + JetBrains Mono — including for numbers, where the old convention was a distinct mono face), a rounded-square "F." mark (replacing the two-cube wireframe logo). Now moot since the sidebar is light too and `.btn-logout` has one consistent light-surface style, but the general lesson stands — a shared class used on two different-colored surfaces needs a surface-scoped override, not one flat color set.
- **This iteration was prototyped as an Artifact first, specifically because iteration 2 (CSS-only, no live preview) shipped a real bug** (the invisible button above) despite careful code tracing. The Design-canvas Artifact let the user actually see and approve the direction before any app code changed — recommend the same approach (prototype → approval → implementation) for any future substantial visual change, rather than iterating blind directly on the app's CSS again.
- **Now verified against a live browser**, on the real deployed site (see Deployment below) — login, dashboard, and navigation were confirmed working by the user on `https://app-finan.github.io/` (the earlier address before the 2026-09-21 move was `mccombmatheus.github.io/financegold/`). Fixed to use `var(--shadow-accent)` like every other accent shadow. When changing the design again, grep for raw hex/rgba values in `style.css` before calling it done — `grep -n "#[0-9a-fA-F]\{3,6\}\|rgba\?(" css/style.css` — most hits are legitimate (the intentionally-always-dark `.auth-brand` panel, white-on-color text), but it's how this one was actually found.

General lesson: any change to the offline-fallback logic in `sw.js` needs to be checked against "cache miss + network failure" as its own case, not just "cache hit" and "cache miss + network success."

### Security posture

There is no backend, so the real access-control boundary is always Google's OAuth + each spreadsheet's Drive sharing settings — everything below is defense-in-depth on top of that, not a replacement for it. Recap for whoever owns the spreadsheets: share each company's sheet only with the specific people who need it (not "anyone with the link"), and keep those Google accounts protected (2-step verification) — that is the actual lock on the data, more than anything in this codebase.

What was audited and confirmed (2026-09, prompted by a user request to harden the app):
- **No XSS sinks.** Every dynamic DOM write in this codebase goes through `textContent`/`createElement`, never `innerHTML` with untrusted content — the only `innerHTML` uses in the whole app are `= ""` to clear a container. No `eval`, `new Function`, or `insertAdjacentHTML` anywhere. This means a malicious value typed into any sheet cell (Observação, a person's name, etc.) renders as inert text everywhere the app displays it, never as executable markup.
- **No formula injection.** All writes go through `updateSheetRow` with `valueInputOption=RAW` (see the earlier note on why), which never interprets a leading `=` as a formula — a cell value like `=IMPORTXML(...)` typed into Observação is stored as literal text, not a live formula. Don't switch any write path to `USER_ENTERED` without re-considering this.
- **No token leakage.** The access token is only ever sent via the `Authorization` header (one unavoidable exception: `getTokenScopes` in `js/auth.js` calls Google's own `tokeninfo` endpoint, which Google's API design requires as a query param — that's Google's endpoint contract, not a choice made here). Nothing logs the token to the console; it lives only in the `accessToken` JS variable and, for session resume, in `sessionStorage` (cleared on tab close, per-tab, never `localStorage`). **One deliberate carve-out since 2026-10-10**: an e-mail+senha session opted into "Manter conectado neste aparelho" is also kept in `localStorage` — see "Manter conectado" below for the reasoning and the limits on it. The Google OAuth token itself is untouched by this and still never leaves `sessionStorage`.
- **Added a CSP** (`<meta http-equiv="Content-Security-Policy">` in `index.html`): scripts restricted to `'self'` and `accounts.google.com`, `connect-src` restricted to the specific Google API hosts this app actually calls, `object-src 'none'`. This is defense-in-depth against any *future* injection point, not a fix for a found vulnerability — none was found. `style-src` needed `'unsafe-inline'` because a few spots (`js/charts.js`) set `.style.background`/`.style.transform` directly, which CSP treats like inline styles.
  - **This was not tested against a live browser** (no browser-driving tool was available in this environment) — only reasoned through against the app's actual external dependencies (just the GIS script + the Google API hosts already used). If login or anything else breaks after this change with a CSP error in the console, that's the meta tag being too strict; loosen the specific directive it names rather than removing the whole policy.
  - A `<meta>` CSP is what's available for a plain static file server; if this app is ever deployed behind a real host/CDN, setting the same policy as an actual HTTP response header there would be strictly better (supports `frame-ancestors`, reporting, etc., which the meta-tag form can't do).

A second pass (same request, "teste-as" — actually go looking, not just confirm) found one real, fixable issue and one robustness gap:

- **CSV formula injection — found and fixed.** `js/export.js`'s `toCsvValue` exported sheet fields (Observação, Produto, a person's name...) into `.csv` files verbatim. Excel (and some other spreadsheet readers) treats a cell starting with `=`, `+`, `-`, `@`, tab, or CR as a live formula when a CSV is opened — this is the well-known "CSV Injection" class (OWASP), distinct from the Sheets-side formula-injection point above and *not* covered by the `RAW`-write mitigation, since it's a read/export path, not a write. Anyone with Editor+ sheet access (or a corrupted entry) could plant something like `=HYPERLINK("http://evil.com","click")` in a field that later gets exported and opened in Excel by Master or an Editor. Fixed with `neutralizeFormulaValue` — a value starting with one of those characters gets a leading `'` prepended, which spreadsheet apps read as "force text," so the payload displays as inert text instead of executing. Verified against both malicious inputs and legitimate text that happens to start with `-` (still gets the safe prefix, still correct) using a small Python simulation of the same regex — no JS runtime was available to unit-test the actual file directly.
- **Tenant email lookup didn't normalize case — fixed.** `js/usuarios.js`'s `fetchUsuario` already lowercased/trimmed both sides before comparing emails, but `js/app.js` did a raw `TENANTS[email]` lookup with no normalization. Not an access-control hole (a mismatch fails *closed*, denying a legitimate user rather than admitting an illegitimate one) but a real robustness bug — fixed with `lookupTenants(email)` in `js/tenants.js`, which normalizes before comparing, matching the pattern already used elsewhere. Both call sites in `js/app.js` now go through it; don't reintroduce a raw `TENANTS[...]` lookup.
- **Re-confirmed no open-redirect / URI-injection surface**: no `window.open`, `location.href`/`.assign`/`.replace`, or `javascript:` URI anywhere in the codebase; the only dynamic `.href` assignment (`js/export.js`) points at a `Blob` object URL the app itself created, never at anything derived from sheet data or user input.
- **Still not live-browser-tested** (same limitation as the CSP note above) — for anyone who wants to verify by hand: try entering `<script>alert(1)</script>` or `=1+1` in an Observação field and confirm it renders/exports as inert text, and watch the DevTools console for CSP violation warnings during normal use.

### Offline support

Requested by the user specifically for a power/internet outage scenario: the app should keep showing the last-loaded data, and let new lançamentos/peças entered offline sync automatically once the connection returns.

- **`sw.js`** (project root — a service worker's scope is the directory it's served from, so it has to live at root to cover `/js/*` and `/css/*`) caches the app shell (every HTML/CSS/JS file, listed by hand in `APP_SHELL`) on install, and serves same-origin GET requests **network-first with the cache as the offline fallback** (`fetch(..., { cache: "no-cache" })`, so GitHub Pages' 10-minute HTTP cache can't hide a fresh deploy either). It was cache-first-with-background-refresh originally and that caused a real bug once the app was live: a phone that had already visited the site kept showing the pre-mobile-layout CSS after the mobile deploy (the new version only arrived on the *next* load), which looked like "the mobile CSS doesn't work" in a user screenshot when the live file was actually correct. `js/sw-register.js` also reloads the page once when a new worker takes control (only if a previous one was already controlling it). Note the first phone/browser that still runs the *old* cache-first worker needs one manual reload after this ships, because its already-loaded page predates that reload listener. It deliberately **never intercepts cross-origin requests** (`sheets.googleapis.com`, `accounts.google.com`, etc.) — those always hit the network directly, since a cached API response would be stale or wrongly-authorized. Registered by `js/sw-register.js`. Requires HTTPS in production (browsers exempt `localhost` specifically, which is why it works over plain `http://localhost:8080` today).
  - **Bump `CACHE_NAME` whenever you change a cached file's content, and keep `APP_SHELL` in sync with the actual `<script src>` list in `index.html`.** The install/activate handlers only re-fetch and evict old caches when the name changes — editing `css/style.css` or any `js/*.js` file without bumping the version means anyone with the old service worker already installed keeps serving stale content from cache indefinitely. Add any new JS file to `APP_SHELL` in the same change that adds its `<script>` tag.
- **`js/offline.js`** is the shared module everything else below builds on:
  - `isNetworkError(err)` — the load-bearing heuristic for this whole feature. A raw `fetch()` failure (genuinely offline) throws a `TypeError` *before* getting any HTTP response; every error this app throws deliberately is a plain `Error` with its own message (thrown only after checking `response.ok`, i.e. we know we're online and the API said no). So `err instanceof TypeError` reliably means "no connection," never "the server rejected this." Don't reuse this check without keeping that distinction in mind if a new error type is ever introduced elsewhere.
  - **Data cache**: `fetchWithOfflineFallback(fetchFn, cacheName, serialize, deserialize)` runs a live fetch and caches the result (`localStorage`, keyed by `cacheName` + the current `CONFIG.SPREADSHEET_ID` so different companies' caches never mix); on a network-specific failure it falls back to the last cached value instead of throwing, returning `{data, fromCache}` either way. A real API error (permission, bad request) still throws normally — silently showing stale data for a genuine rejection would be worse than an error message. `serializeLancamentos`/`deserializeLancamentos`/`serializeEstoque`/`deserializeEstoque` exist because `.data`/`.dataCompra`/`.dataVenda` are JS `Date` objects, which survive `JSON.stringify` (via `toJSON`) but not `JSON.parse` (comes back as a string) — these convert explicitly both ways. Lookups need no such wrapper (plain data, no dates).
  - **Write queue**: `enqueueWrite(type, payload)` appends to a `localStorage` array (also keyed by spreadsheet), for the two *creation* flows only (see below). `flushQueue()` replays queued items in order on the `online` event (or right after a successful load, if a queue was left over from last time) using the exact same submit functions the live UI uses — `submitLancamentoValues` (`js/form.js`) and `createEstoqueItem` (`js/estoque.js`) — so there is exactly one code path for "create a lançamento," online or replayed. An item that still fails for network reasons stops the flush (keeps the rest queued, order preserved); one that fails for a real API reason is dropped with a visible warning rather than jamming the queue forever.
  - `describeSaveError(err)` — a friendlier "sem internet" message for the handful of actions that are deliberately **not** queued (see below), instead of surfacing a raw "Failed to fetch."
- **What's queued vs. not, and why**: only the two *creation* forms — "Novo lançamento" and "Nova peça" — get offline queueing. Estoque's state-changing actions (mark custody, return to store, mark sold) do **not** queue: they target one specific existing row and read its *current* `Observação`/fields at click time to compute the write; blindly replaying that later, after who-knows-what else may have changed that row in the meantime, risks silently overwriting someone else's intervening edit. A creation is just "add a new row," which has no such conflict — safe to defer. Those un-queued actions instead fail loudly with `describeSaveError`'s "isso precisa de internet" message when offline.
- **Resuming a session while offline is the trickiest part, and was a real bug found while building this**: a `sessionStorage` token from an earlier login can be read with zero network calls, but `handleSignedIn`'s normal path still needs two live round-trips (verify scopes, fetch email) before it knows who's logged in — without a fallback, reloading the page while offline hung forever on "Verificando conta...", unable to ever reach the cached data underneath. Fixed via `js/app.js`'s `saveLastSession`/`loadLastSession`/`enterOfflineFromLastSession`: every successful `startApp` snapshots `{email, spreadsheetId, sheetName, empresa, nome, perfil, linha}` to `localStorage`; if the scope/email checks fail with a network error specifically, `enterOfflineFromLastSession` trusts that snapshot instead of re-verifying it, and proceeds straight into `startApp` (which itself falls back to the data cache as usual).
- **Being offline is silent by explicit user request**: no "Sem internet — mostrando os últimos dados" banner or status line (both `updateOfflineBanner` in `js/offline.js` and the `anyFromCache` branch in `js/app.js` now show nothing). The one exception kept on purpose: `#offline-banner` still appears when there are offline-entered lançamentos/peças waiting to sync ("N pendente(s)..."), because hiding that would make a saved entry look like it vanished. The per-form confirmation ("o lançamento foi guardado e será enviado...") and `describeSaveError`'s "isso precisa de internet" for un-queued actions are also unchanged — they answer something the user just tried to do.
- **A page reload resumes where the user was**: the chosen company (`rememberCompany`/`loadRememberedCompany` in `js/app.js`, key `financegold_company`) and the active screen (`LAST_VIEW_KEY` + `restoreLastViewOnce` in `js/nav.js`) are kept in `sessionStorage`, so with a still-valid token a reload goes straight back in instead of to the company picker. This was found live: a user with two companies got the picker on every reload, and its brand-panel layout is nearly identical to the login screen so it read as "kicked back to login". Both keys are cleared by the three logout handlers (`forgetSessionPlace`). The view is restored only once per page load and only if that nav item isn't role-hidden. If a reload ever shows the real login screen (the "Continuar com Google" button) within an hour of logging in, that is a different problem — the token in `sessionStorage` is missing or was rejected by `getTokenScopes` in `handleSignedIn`.
- **Signing out clears the cached data** (see the security pass): only the queue of unsent offline entries survives an explicit sign-out; an expired session keeps everything so the person resumes after signing in again.
- **Real limits, stated plainly rather than oversold**:
  - This only works for **up to roughly an hour** after the last successful login — that's the lifetime of a Google OAuth access token in this app's flow (GIS token-client, not a refresh-token flow, by design — see `js/auth.js`), and there's no way to silently renew it without network. A multi-hour outage will eventually require a fresh (online) login.
  - **A first-ever login cannot happen offline** — identifying who you are is inherently a network operation (Google OAuth). Offline support covers "I was already using this app," not "I'm opening it for the very first time with no connection."
  - **No conflict resolution.** Two people offline at once, or someone editing the live sheet while another device is queued, isn't reconciled — last write wins, silently. Acceptable for this app's small-team scale; would need real work to generalize further.
  - **Not tested against a live browser** (no browser-driving tool was available in this environment) — verified by careful code tracing of every path (online, offline-with-cache, offline-with-no-cache, offline session resume, queue flush, partial queue failure) instead. Ask the user to verify with Chrome DevTools → Network → Offline before trusting this in a real outage.

### Apps Script gateway (access without Drive sharing)

`apps-script/Code.gs` (+ `appsscript.json`, `LEIA-ME.md` with the deploy steps) is a Google Apps Script web app that runs **as the spreadsheet owner** and sits between the browser and the spreadsheets. It exists because direct mode needs every user's own Google account to have the spreadsheet shared in Drive, which cannot be automated from a static app without asking for the full `drive` scope. **It is switched on by setting `CONFIG.GATEWAY_URL` in `js/config.js`** — now set to the deployed `/exec` URL, so the app runs in gateway mode; emptying it falls back to the original direct mode (each user's own token → Sheets API, Drive sharing required). The deployed endpoint was smoke-tested with `curl` (note: use `curl -L -d ...` *without* `-X POST`, or curl re-POSTs to the redirect target and gets an HTML error page — browsers do it correctly): it refuses an invalid token and a missing token, rejects a non-JSON body, and answers with `access-control-allow-origin: *`.

- **This file is the access-control boundary in gateway mode**, not the UI. Every request: `verifyGoogleToken_` (tokeninfo; the token's `aud` must equal this app's `CLIENT_ID`, email must be verified) → look the email up in that spreadsheet's `Usuários` tab (`getAccess_`, 20 s cache dropped on every Usuários write) → check the role against the action. Roles are enforced server-side: Visualizador reads only (data tabs, never `Usuários`); Editor also writes the company's ledger tab and `Estoque`; Master also reads/writes `Usuários` and creates that tab; any listed user may change only their **own** Nome cell (`B{their linha}`). Reads/writes are limited to `SPREADSHEETS` (ids in the script), to the tabs in `READ_TABS`/`WRITE_TABS`/the company `sheetName`, to a strictly parsed A1 range, and to one row of ≤20 scalar cells ≤2000 chars.
- **Bootstrap**: a company whose `Usuários` tab is missing/empty can be set up only by an email in `ADMIN_EMAILS` (creates the tab, writes the header, and writes *its own* Master row — nothing else). Once anyone is listed that door is closed even for the admin. `me` returns `{companies, bootstrap}` and is how the client discovers companies and its own role (`resolveCompaniesForEmail`/`fetchUsuario` in gateway mode) — `js/tenants.js` routing is unused in gateway mode.
- **Login scope shrinks to `userinfo.email` only** (`CONFIG.SCOPES` is computed from `GATEWAY_URL`), so users' tokens can no longer touch Sheets/Drive at all, and the OAuth consent screen can be **published to production without Google verification** — which also removes the "Test users" step and the 7-day token expiry of Testing mode. The spreadsheets then only need to be shared with the owner.
- Writes use the advanced Sheets service with `valueInputOption: RAW` (so `=...` stays literal text, dates stay serials, same as direct mode). `js/sheets.js` `gatewayCall` posts `text/plain` on purpose: a simple request has no CORS preflight, which Apps Script web apps cannot answer; the token travels in the body. HTTP status is always 200 from Apps Script — success/failure is `{ok, error}` in the body, turned into a normal `Error` (a real network failure stays a `TypeError`, so the offline logic still works). CSP `connect-src` allows `script.google.com` and `script.googleusercontent.com`.
- **Tested** (in headless Chrome, since Apps Script can't run locally): the authorization logic is pure functions over injected dependencies (`handleRequest(body, deps)`), exercised by a 63-case suite (bad tokens, every role × action, self-promotion, bootstrap abuse, range/value injection, cache invalidation) plus a 15-case client↔gateway run with `fetch` mocked to the real handler. **Not tested against the real Apps Script runtime or the real tokeninfo endpoint** (no way to run either here) — the first real deploy is the first time `verifyGoogleToken_`, the `Sheets.*` advanced-service calls, and the CORS behavior of the `/exec` URL run for real. Verify with a Visualizador account that cannot open the spreadsheet in Drive.
- Known limits: unauthenticated callers can still make the script spend `UrlFetchApp` quota on tokeninfo (Apps Script's own quotas are the only rate limit); each request adds Apps Script latency (~0.3–1.5 s) compared with calling the Sheets API directly; two people saving at once can still race for the same "next row" (unchanged from direct mode; the script only serializes the write itself with a lock).

A full audit before launch. Checked and clean: no `innerHTML` with dynamic data (only the two documented constant-icon spots), no `console.log`/TODO leftovers, `sw.js` `APP_SHELL` in sync with every `<script src>`, no duplicate/missing element ids, balanced HTML, and every screen rendered in headless Chrome at 320, 390, 768 and 1280–1440px with no JS errors and no horizontal overflow (see the layout-testing note under Visual design system). Fixed/added as a result:

- **A large KPI value could get its last digit clipped (reported 2026-10-11, live site, real numbers)**: `.stat-value` is `white-space: nowrap` inside `.stat-tile`'s `overflow: hidden`, with a fixed `1.9rem` (span-3 tiles) — a 7-figure BRL value like "R$ 1.806.598" is wider than that at a typical window width and the overflowing tail was silently cut off rather than wrapped (nowrap was deliberate, see the note above, but nothing previously shrank the font for a long value). ### Adaptive spreadsheets (any layout, any tab names)

Requested so other companies can bring their own sheets: columns in any order, extra columns, other words ("Receita/Despesa", "Descrição", "Qtd"), dates and money as text, titles not on row 1, tabs named differently. No AI/backend: heuristics in plain JS, tested.
- **`js/esquema.js`** (pure functions): `detectarEsquema(rows, papel)` finds the header row (first 15 rows; a row with "3 - Nome" codes or <30% recognised cells is data, not a header), matches columns to fields by name (accents/case/stop-words, synonym lists `CAMPOS_LANCAMENTO`/`CAMPOS_ESTOQUE`, one-typo tolerance, exact > extra-words > typo) and by content when a title is missing (dd/mm/yyyy strings -> date, Entrada/Saída values -> type); no recognisable header -> the original positions (`POSICOES_PADRAO`, flagged `incerto`). Unrecognised columns become **extras** (shown in the list/cards/CSV, search, and as optional inputs in the forms). It also learns the sheet's habits: words for in/out (`rotuloEntrada/Saida`), whether expenses are written negative or positive (`saidaNegativa`), whether values carry "N - " codes. `interpretarLancamentos`/`interpretarEstoque` convert rows (real row numbers; dates from serials, "dd/mm/yyyy", ISO, "1 de março de 2026"; money "R$ 1.234,56", "(50,00)"; Receita/Despesa -> Entrada/Saída; expenses normalised negative). Rows without a date (a "Total" line) are ignored and counted (`ultimoResumoLeitura`, shown in the load status). `interpretarLista` reads support lists (with or without header; names only; code+name). A standard sheet reads **byte-identically** to the old positional code (tested against a copy of the old parsers).
- **`js/abas.js`**: tab names per role (`nomeAba(papel)`: defaults "Lançamento"/"Estoque"/"Lojas"..., overridden by the company's **`Configuração`** tab), `intervaloAba` (always quotes/escapes the tab name), the saved layout per spreadsheet (`guardarEsquema`/`obterEsquema`, kept in localStorage so forms know where to write offline), `lerLinhasDaAba` (plain-language error when a tab does not exist, pointing the Master to "Conectar planilha"), `acharProximaLinha` and **`escreverColunas`**.
- **Writes touch only the cells the app fills** (`colunasParaEscrever` -> contiguous blocks, key column block last): a formula column filled down the sheet, a "Total" line or any unrecognised column is never overwritten, and a connection drop half-way leaves no orphan row. The next row comes from the key column (Data/Produto) but skips any row where a recognised column is occupied.
- **`js/lookups.js`**: each list comes from its tab (default or configured, any layout); when the tab is missing/empty the options are **learned from the values already typed** in the ledger/stock column. Categoria only offers rows whose status is explicitly "Ativo" when a status column exists.
- **Connecting a sheet with other tab names** — Ajustes → *Conectar planilha* (`js/conectar.js`, Master only): "Analisar planilha" reads every tab (the Master may read any), suggests a role per tab (`classificarAba`, `adivinharLista`), the Master corrects and saves; that writes `Configuração` (Papel, Aba) and reloads. The card also shows exactly how each column of the ledger/stock was understood (title row, recognised columns, missing fields, extras). Only non-default tab names are stored; a standard sheet has no `Configuração` tab. The "Listas de apoio" editor (which assumes the standard list tabs) is hidden for companies with connected lists.
- **Gateway** (`Code.gs`): reads/writes of tabs are authorised by `READ_TABS`/company `sheetName` **plus** the tabs named in `Configuração` (`loadConfigTabs_`, 20 s cache, dropped on write); Master may read any tab; only the Master writes `Configuração` (`validConfigRow_`: exact header or a known role + a tab name that is never `Usuários`/`Configuração`, ≤30 rows); rows up to 60 cells (`MAX_ROW_CELLS`); non-Masters only see the names of tabs they may use (`titlesFor_`). A hostile `Configuração` typed straight into the sheet cannot open `Usuários`.
- Works with the **old server** too (default names need no server change); Conectar and segments need the new `Code.gs` deployed (version stamp `2026-09-20-planilhas-adaptaveis`).

### Reloading the page (2026-09-20: "ao atualizar, volta para a página anterior e dá erro")

Two real causes: (1) on a reload the login screen showed ("Verificando conta...") while the account was checked, then the app opened on the Dashboard and only then jumped to the screen the person was on; (2) any hiccup of Google or of the Apps Script server during that check (they do happen: occasional 404/302/HTML answers) **erased the session and sent the person to the login screen with an error**. Now: `js/inicio.js` (in `<head>`) adds `html.retomando` when this tab already has a valid session, which shows `#boot-screen` ("Carregando…") and hides `#login-screen`; `hideAllScreens()` removes it as soon as any real screen is shown (a 25 s safety net removes it anyway). `startApp` sets up and chooses the remembered screen BEFORE `showApp()` (no dashboard flash). The sign-in reads (`getTokenScopes`, `fetchUserEmail`, `resolveCompaniesForEmail`, and the access check in `resolveProfileAndEnter`) go through `tentarVariasVezes` (2 retries, 1.2 s / 2.5 s; never for offline, expired session, 401/403); a persistent failure shows the login screen with a plain explanation **but keeps the session** so a reload resumes; only a refused/invalid token (401 / tokeninfo 4xx) signs out; Google 5xx/429 is a hiccup, not a bad token. Errors carry `.status` (gatewayCall / auth.js). `showLogin()` is called before any login-screen message (the login screen is hidden while resuming). Tests: `routes.html` suite (reload/flash/retry/keep-session cases; fails when the old order or the old sign-out is restored).

### Login needed two tries (2026-09-20: "clico no meu e-mail, ele volta, clico de novo e entra")

Not reproducible without a real Google login, so every plausible first-try failure was removed (each has a test in the `routes.html` suite): (1) **the token check right after login**: `handleSignedIn` asked Google's tokeninfo about a token issued a moment earlier; Google can briefly not know it (or answer 5xx) and the person was bounced to login. Now the scopes Google reports in the login callback (`response.scope`) are kept in `sessionStorage` (`SESSION_SCOPES_KEY`, with `SESSION_ISSUED_KEY`) and used instead (also on reload: one network call fewer); a 401/400 or a null about a token younger than 90 s (`tokenEmitidoHaPouco`) is asked again (`escoposDoToken`, `emailDoToken`). (2) **Pop-up blocked on the first click**: the click handler did `await authReady` before opening Google's window, which strict browsers (Safari/iOS) can refuse; now, once the Google client exists, `requestAccessToken()` runs in the very same click. (3) **Silence on failure**: `initTokenClient` now has an `error_callback` and the callback's `error` goes to `mostrarErroDeLogin` (blocked pop-up, closed window, denied consent, anything else) instead of only the console. (4) **Apps Script answering a web page instead of data** (seen on fresh deployments): `gatewayCall` asks READ actions again up to 2 times (invalid JSON or 503 "busy"); writes are never repeated.

### Login with e-mail + password (alternative to Google sign-in)

Requested so people without a convenient Google flow can enter. Same allow-list model: a password login only proves *who* someone is; roles/companies still come from each company's `Usuários` tab, and the system administrator must **approve** every new login (e-mail with the request goes to `ADMIN_EMAILS`; decision in Painel do sistema → "Logins com senha", `carregarLoginsSistema` in `js/sistema.js`).

- **Client** (`js/senha.js`, `js/login-senha.js`, screens in `index.html`: `#login-senha-bloco`, `#senha-cadastro-screen` (dados → código → pronto), `#senha-esqueci-screen`, `#ajustes-senha-card`): the password never leaves the browser. `derivarChaveDeSenha` = PBKDF2-SHA256, 210,000 rounds, salt `"finan.v1:" + canonical e-mail`, NFKC-normalised password → 43-char base64url key; only that key is sent. `avaliarSenha` gives the strength meter and refuses short/common/e-mail-derived passwords. Every password field has a "ver senha" toggle; "Trocar senha" lives in Ajustes (shown only for password sessions, `prepararCartaoDeSenha`).
- **Server** (block "Login with e-mail + password" at the end of `apps-script/Code.gs`): stores in the registry spreadsheet's `Logins` tab `HMAC-SHA256(PW_PEPPER, randomSalt|key)`, never the password or key. Flow: `pwRegister` → e-mailed 6-digit code (hashed, 15 min, 5 tries) → `pwConfirmar` → status waits for admin (`pwListar`/`pwDecidir`: aprovar/recusar/bloquear/reativar) → `pwLogin` returns a stateless session token `fs1.<hexEmail>.<exp>.<versão>.<hmac>` (12 h; changing the password or blocking bumps the version and kills old sessions). `pwEsqueci`/`pwRedefinir` reset via e-mailed code; `pwTrocarSenha` needs a password session. Public actions take no token and answer generically (no e-mail enumeration; same reply for unknown and known e-mails); 5 wrong passwords lock 15 min (also for unknown e-mails, via cache counters); mail limits: 60 s cool-down, 5 per address per 6 h, 60/h global. Constant-time compares; SHA-256/HMAC are pure JS in `Code.gs` (verified against official vectors) so the exact same code runs in the headless-Chrome test suite (Apps Script's `Utilities` cannot run there).
- **Secrets** `PW_PEPPER` and `PW_SESSION_KEY` are auto-created in Script Properties on first use. **Losing them invalidates every password and session** (people then use "Esqueci minha senha"). A gateway created for a new account (e.g. the migration) starts with new ones.
- Client session bookkeeping in `js/auth.js`: `saveSenhaSession`, `tipoDeSessao()`, `emailDaSessao()`; `handleSignedIn` routes password sessions straight to `seguirComConta` (no Google token checks). `signOut` skips the Google revoke for them.
- **Deploying needs the new `Code.gs` pasted into the Apps Script and a new version**; until then the password screens get the gateway's "unknown action" error. `loginComSenhaDisponivel()` only checks that `GATEWAY_URL` is set (direct mode has no password login).
- Tests: `apps-script/testes/permissoes.html` (336 cases incl. lifecycle, lockout, forged sessions, enumeration equality, admin actions), client flows in the routes harness. **Not run against the real Apps Script/MailApp** — first real run is the first time `MailApp` sends the codes. The KDF-vs-independent-PBKDF2 check needs a page without the ui harness (native WebCrypto stalls under `--virtual-time-budget` if the page has no timers pending; also add `<meta charset="utf-8">` to scratch pages or non-ASCII test strings get mangled and fail spuriously).

### "Manter conectado neste aparelho" (2026-10-10)

Reported: closing the app (not clicking "Sair") always forced a login again next time, even moments later — asked directly ("conseguiríamos manter ele logado de alguma forma?"), answered with the real tradeoff before touching any code (see that chat turn), then built once the user picked the e-mail+senha-only approach.

- **Why Google sign-in can't do this**: its access token lasts ~1h, full stop — this app's flow (Google Identity Services' token client, no refresh token; see `js/auth.js`) has no way to renew it silently, by design, long before this feature. Moving *that* token into `localStorage` would only let it survive a closed tab within its own hour, not give a real "stay logged in" — not worth the tradeoff below for that little gain. **The Google OAuth token is completely untouched by this feature and still lives only in `sessionStorage`.**
- **The e-mail+senha login is the app's own invention** (see that section above), so its session length was already just a constant (`PW_SESSION_MS`, 12h) the server controls — a real "remember me" was simply a matter of issuing a longer one on request and keeping it somewhere that outlives a closed tab.
- **Client** (`js/auth.js`): a checkbox, `#login-lembrar` (index.html, "Manter conectado neste aparelho", only on the e-mail+senha form — Google sign-in has no such control, nor could it do anything with one). Checked at login, `js/login-senha.js` sends `lembrar: true` to `pwLogin` and, on success, `saveSenhaSession(token, expiraEm, email, true)` writes the session to **both** `sessionStorage` (unchanged, for this tab) **and** a separate set of `localStorage` keys (`financegold_lembrar_token`/`_expira_em`/`_email` — new, distinct from the Google ones, which stay sessionStorage-only). `loadValidTokenFromSession()` — the one function the boot sequence already called — now falls back to the `localStorage` copy when this tab's own `sessionStorage` is empty (a reopened tab/app) and *promotes* it into `sessionStorage`, so every other function (`tipoDeSessao`, `emailDaSessao`, `signOut`...) keeps reading from the one place it always did; nothing downstream needed to learn about `localStorage` at all. `js/inicio.js`'s head-script boot check (`deveRetomarSessao`, generalized to take any storage + key names) now also checks the `localStorage` copy, so a resumed remembered session gets the same quiet "Carregando…" boot screen as a same-tab reload, not a login-screen flash.
- **Server** (`Code.gs`): `PW_SESSION_LONGA_MS` (30 days) alongside the existing `PW_SESSION_MS` (12h); `emitirSessao_` now takes a duration parameter (defaults to the 12h constant, so every untouched call site is unaffected); `acaoPwLogin_` picks the long one when `body.lembrar === true`. **`pwTrocarSenha` (change password while signed in) honours the same flag** — found while building this: without it, someone remembered on a device who changes their password from inside the app would silently get downgraded to a 12h session, since the old code always re-issued the default length. `js/login-senha.js`'s trocar-senha handler now checks `Boolean(loadRememberedSenhaSession())` before calling it, so a password change preserves whichever state (remembered or not) the session already had, never guesses.
- **The real tradeoff, stated to the user before building this**: a session that survives closing the app is a session sitting in that browser's storage until it expires — fine on a personal phone/computer, a real exposure on a shared/public one. No code can tell those apart; it was a plain conversation, not a setting. The **kill switch**, unchanged from before this feature: changing the password or an admin blocking the login (`pwDecidir`, "bloquear") bumps `LG.VERSAO`, which invalidates every outstanding session at once, the 30-day ones included — confirmed by test (below), not just reasoned through.
- **Tested**: `apps-script/testes/permissoes.html` grew to **383 cases** (6 new, in their own isolated `mundo()` world so the password changes they make don't bump the version out from under the `tok` variable the rest of that suite keeps reusing afterward — a real near-miss caught while writing these, worth remembering for any future test that changes a password mid-suite) — `lembrar:true` issues exactly a 30-day session, `lembrar:false`/omitted keeps the normal 12h one, `pwTrocarSenha` preserves either, and a version bump kills a 30-day session exactly like a 12h one. All 383 pass. Client-side (`js/auth.js`'s storage functions, `js/inicio.js`'s boot check), verified against the real shipped files in headless Chrome, not just traced: `lembrar:true` writes to both storages, `clearTokenSession` (every "Sair" button, and a real 401 from the server) wipes both, a "reopened tab" with only the `localStorage` copy resumes and promotes correctly, an **expired** remembered copy does not resume, and `lembrar:false` never touches `localStorage` at all. **Not tested here**: a real `pwLogin`/reopen-the-app round trip in an actual browser profile — ask the user to check the checkbox, close the whole app (not just "Sair"), and confirm it reopens signed in.
- **`sw.js`**: no new files (only already-shelled ones changed); `CACHE_NAME` bumped to `v51`.

### ERP, Fase 1 (2026-10-08): Fornecedores, Contas a Pagar/Receber, Relatório

Requested as the first phase of turning the app into an ERP+CRM, scoped and approved first as a chat roadmap and a Design-canvas mockup (same "prototype before building" pattern as the visual redesigns), then built. Sticks to the existing architecture on purpose: more Google Sheets tabs + more gateway tab names, no new backend, same role model, same offline/CSV/security conventions — "a bigger app," not a rewrite.

- **Three new tabs, each fixed/positional (like `Usuários`), NOT routed through the adaptive `esquema.js` engine** `Lançamento`/`Estoque` use — a deliberately smaller first step. "Conectar planilha" does not offer them a custom tab name yet; that's a reasonable follow-up, not done here.
  - **`Fornecedores`** (`js/fornecedores.js`/`js/fornecedores-ui.js`, nav: Compras → Fornecedores / Novo fornecedor): Nome, CNPJ/CPF, Categoria, Telefone, E-mail, Prazo de pagamento, Observação, Status. **Deactivating, never deleting** — `setFornecedorStatus` flips Status Ativo/Inativo (Categoria's own convention) rather than blanking the row, because Contas a Pagar references a fornecedor by free-text name and losing the row would lose that history.
  - **`Contas a Pagar` / `Contas a Receber`** (`js/contas.js`/`js/contas-ui.js`, one generic module parametrized by `tipo: "pagar"|"receber"` — `CONTAS_CONFIG`, nav: Financeiro group): Descrição, Fornecedor/Cliente (free text — separate from the `Pessoa` lookup on purpose, see below), Categoria, Valor, Vencimento, Status (`Pendente`/`Pago`|`Recebido` — **`Atrasado` is never stored**, only computed client-side, `ehContaAtrasada`, from Vencimento < hoje, so there is no background job to keep a stored status in sync), Pago em/Recebido em, Recorrente (Sim/Não), Observação, Avisado em (dedupe key for the e-mail reminder, below).
- **Settling a conta ("Pagar"/"Receber") does three things as one unit, in `settleConta`** (confirmed with the user: automatic, not a two-step "ask first"): (1) writes the matching **Lançamento first**, through `submitLancamentoValues` (`js/form.js`) — the exact same function the "Novo lançamento" form and the offline queue already use, so there is still exactly one code path for "a lançamento happened"; (2) only then marks the conta settled, with an `Observação` note pointing at the lançamento row just written, so the link is traceable by eye; (3) if `Recorrente`, rolls the next occurrence forward a month (`proximoMes` — same day-of-month, clamped to the target month's last day for a 31st rolling into a shorter month) as a fresh `Pendente` row — **no cron/trigger needed**: the next occurrence simply doesn't exist until the current one is paid, which is also why a recurring bill needs its first occurrence entered once by hand. The settle panel (`showContaSettlePanel`) asks for Loja/Conta/Empresa/Categoria/Pessoa — the conta itself doesn't capture these, since Lançamento requires them and a Pessoa lookup match (by name) is attempted but not assumed. **Caught by testing, not reasoned through**: a naive first test of this double-write made it look like the recurring rollover could clobber the just-settled row; a stateful mock (tracking what `updateSheetRow` actually wrote, like the real sequential-awaited backend would) showed the real code is correct — `findNextContaRow`'s read always happens *after* the settle write completes, so it never lands on the same row. Worth remembering if this function is touched again: test it against a stateful fake sheet, not one that answers every read the same way regardless of order.
- **Avisos de vencimento by e-mail, to Editor + Master only** (confirmed with the user — Visualizador can't act on a bill, so doesn't get mailed): `actionVerificarLembretes_` in `Code.gs`, a gateway action, **checked once per login** (`js/app.js`'s `startApp`, fire-and-forget, gateway mode + `canEdit` only) — "checked whenever someone who can act signs in," not a true any-time push on its own (see the daily trigger below, which now covers the gap). Dedupe is **per-row**, via each conta's own `Avisado em` column (today's date serial) rather than a cache key — correct across different people/devices logging in the same day, and across the login path and the trigger path both firing the same day, no special-casing needed. Window: due within `CONTAS_AVISO_DIAS_ANTES` (3) days, or already overdue; a `Pago`/`Recebido` conta is never a candidate. One e-mail per recipient listing every due/overdue item across both tabs, overdue ones marked ATRASADA.
- **Cancelar uma conta (2026-10-11)**: a third, terminal `Status` value, `"Cancelada"` (`STATUS_CANCELADA` in `js/contas.js`), for an entry created by mistake or no longer expected — requested explicitly as distinct from settling (no money actually moved). `cancelConta` writes only the status + an `Observação` note (no `Lançamento`, no recurring rollover: a cancelled `Recorrente` conta's series simply stops, since nothing but a *settle* ever creates next month's row). **No server-side change needed at all** — `Status` was already a free-text cell (`validateRow_` only checks cell type, not an enum) and `executarVerificacaoLembretes_` already only ever considers rows whose `Status` is literally `"Pendente"`, so a cancelled conta silently stops being e-mailed/pushed/WhatsApp'd about for free. `renderContaActions` (`js/contas-ui.js`) now has three branches by status — Pendente shows Pagar/Editar/Cancelar, Cancelada shows only **Reabrir** (`reopenConta`, back to Pendente — mirrors Fornecedores' Inativar/Reativar pair so cancelling is never a dead end), Pago/Recebido still shows nothing (that one stays a true dead end — it already has a matching Lançamento, so undoing it would mean undoing real money moved, unlike Cancelada). The confirm step and error handling (`confirm()` + `alert(describeSaveError(err))`) deliberately match Fornecedores' `Inativar` exactly, the closest existing precedent, rather than the heavier two-step-button pattern Usuários removal uses. Filter dropdowns for both tabs gained a "Canceladas" option; the KPI strip was deliberately left as Pendente/Atrasadas/Pago(Recebido)-este-mês only, not given a fourth "Canceladas" tile (not asked for). **The user also asked for the same capability in "Compras, etc."** — Fornecedores already has the equivalent (Ativo/Inativo, same Inativar/Reativar shape this reuses) — confirm with the user whether that already covers it, or whether they mean something not built yet (Estoque? a future Pedidos de compra module?) before extending this further.

### Aviso de cota de e-mail quase esgotada (2026-10-11)

Requested after a conversation about scaling: `finanponto@gmail.com` is a free Gmail account, and `MailApp` is the ONLY sender for the entire system — access-request mail, password-login codes, the daily bill reminders above — shared across every company, not per-company. Google's free quota is 100 recipients/day; if it's ever exhausted, those e-mails just silently stop sending, with no error anywhere in the app for anyone to notice. The user asked for a standing warning well before that point ("quanto chegar em 90% dessa capacidade"), so there's time to react (e.g. move the account to paid Google Workspace, which has a much higher daily limit — see the scaling notes elsewhere in this file) before anyone is actually affected.

- **`verificarCotaDeEmail_(deps, restante)`** (`Code.gs`) is the pure, testable core: computes `usados = MAIL_QUOTA_DIARIA_ESPERADA - restante` (the constant is **100**, Google's documented free-Gmail `MailApp` limit — `MailApp` itself only ever reports what's left via `getRemainingDailyQuota()`, never the total, so this has to be kept in sync by hand if the account is ever upgraded to Workspace), and if that's ≥ `MAIL_QUOTA_ALERTA_PCT` (**0.9**) of the total, mails `ADMIN_EMAILS` (today, just `finanponto@gmail.com`) a plain-language warning with the exact numbers and what to do about it.
- **Dedupe is once per (UTC) day**, via a new `quotaEmail` dep (`quotaEmailDeps_()`) backed by a Script Property (`MAIL_QUOTA_ALERTA_DATA`) rather than the cache — `CacheService`'s own max expiry is 6 hours, too short to hold "already alerted today" across a full day, the same reason the Contas reminders dedupe through a sheet cell instead of a cache key (see above). Comparing against `new Date(deps.now()).toISOString().slice(0, 10)` (UTC date) rather than matching Google's actual Pacific-time reset instant exactly — it only needs to change once a day, not be perfectly synced with the reset moment.
- **`verificarCotaDeEmailAgendado()`** is the real trigger entry point — calls the real `MailApp.getRemainingDailyQuota()` and the real `realDeps_()`. **`instalarGatilhoCotaDeEmail()`** installs a trigger that runs it **every 2 hours** (not once a day like the Contas reminder trigger) — the whole point is catching the threshold promptly as usage accumulates through the day, not just checking once each morning. Same manual, one-time, idempotent install pattern as `instalarGatilhoLembretes`: open the Apps Script editor, select `instalarGatilhoCotaDeEmail` in the function dropdown, press Run, authorize if asked; re-running it after a redeploy is harmless (it deletes any trigger it previously made for this handler first), but it is **not** re-created automatically just by pasting a new `Code.gs`.
- **Tested**: `verificarCotaDeEmail_` directly — below threshold sends nothing, over threshold mails `ADMIN_EMAILS` exactly once, a second check the same (mocked) day does not re-mail, a different stored date alerts again, and exactly 90% used counts as crossing the threshold (not just >90%). `apps-script/testes/permissoes.html` grew from 419 to **424 cases**, all passing. **Not testable here**: `verificarCotaDeEmailAgendado`/`instalarGatilhoCotaDeEmail` themselves call real `ScriptApp`/`MailApp`/`realDeps_()`, so — like the Contas reminder trigger — they only run for real inside the Apps Script runtime; ask the user to confirm Apps Script → Triggers shows the 2-hour trigger after running `instalarGatilhoCotaDeEmail` once, and that a forced low `restante` (temporarily lowering `MAIL_QUOTA_DIARIA_ESPERADA` in a test run, then reverting it) actually delivers a real e-mail.

### Notificações push + contato de teste no WhatsApp (2026-10-10)

Two channels added to the existing daily `verificarLembretesTodasEmpresasAgendado` trigger, on top of (never replacing) the e-mail reminder: a **push notification**, for anyone in any company who opts in on their device, and a **WhatsApp message**, to one fixed, verified test number (the Ipanema Master). Both are config-gated no-ops until their Script Properties are set — pushing this code live changes nothing by itself.

- **Why Firebase sits in the middle for push, instead of this app speaking raw Web Push**: a real push send needs a VAPID-authenticated request, which is signed with ECDSA over the P-256 curve — Apps Script's `Utilities` class has no elliptic-curve signing at all. It DOES have `Utilities.computeRsaSha256Signature`, which is exactly what authenticating as a **Firebase** service account (Google's own, RSA-based, JWT bearer flow) needs. So: Firebase Cloud Messaging (free, no message limit) does the actual VAPID/browser-specific delivery; Apps Script only ever has to sign one RSA JWT to get a bearer token, then POST a plain JSON message to `fcm.googleapis.com`.
- **Client** (`js/push.js`, loaded via the Firebase JS SDK **compat** build from `https://www.gstatic.com` — added to the CSP's `script-src`; `fcmregistrations.googleapis.com`/`firebaseinstallations.googleapis.com` added to `connect-src` for the SDK's own registration calls): an always-visible "Notificações" card in Ajustes (hidden only in direct mode, which has no `registrarPush` action), `ativarNotificacoes()` asks `Notification.requestPermission()`, gets an FCM token via `messaging.getToken({vapidKey, serviceWorkerRegistration})` (reusing the SAME service worker `js/sw-register.js` already registers — no second SW), and sends it to the gateway. **A real near-miss caught before testing**: the gateway's OWN auth token already lives in `body.token` for every action (`handleRequest` reads it before `despachar_` even runs) — the first draft of `registrarPush` also read the device token from `body.token`, which would have silently registered the caller's own Google/session token string as if it were an FCM token. Fixed by using `body.pushToken` instead; covered by a dedicated test (`apps-script/testes/permissoes.html`) asserting the stored value is the device token and never equals the caller's auth token.
- **Background vs. foreground**: a push sent as a `notification` payload (not a silent `data` payload) is auto-shown by the browser via the service worker **only while the tab isn't focused** — `sw.js` now does `importScripts` for the Firebase compat SDK and calls `firebase.messaging().onBackgroundMessage(...)` → `self.registration.showNotification(...)`, plus a `notificationclick` handler that opens the app. While the tab **is** focused, Firebase instead routes the message to `onMessage` on the page itself (`js/push.js`'s `escutarMensagensEmPrimeiroPlano`), which shows it manually via the plain `Notification` constructor — without this, a push would be silently swallowed whenever the app happened to be open. The SW can't `import` `js/config.js`'s `FIREBASE_CONFIG` as module state (only via `importScripts`), so its six values — all public, non-secret Firebase web config — are duplicated directly in `sw.js`; keep both copies in sync if the Firebase project ever changes.
- **Server** (`Code.gs`): `PushTokens` is a new tab in the **registry** spreadsheet (not a company sheet — a device belongs to a person, not to one company's data, same reasoning as `Logins`), columns E-mail/Token/Criado em/Último confirmado em, with its own bootstrap-the-tab-if-missing wrapper (`pushTokensDeps_`, copy-pasted in the same shape as `loginsDeps_`/`requestsDeps_` — this file already has three near-identical copies of that bootstrap, so a fourth follows the established convention rather than introducing a shared helper). `actionRegistrarPush_` needs no role check beyond having proved who you are (any Google or e-mail+senha session may register their own device — it is opt-in convenience, never a permission grant). Re-registering the same device token re-assigns its owner (overwrites the e-mail) instead of duplicating a row, since a browser/device token can end up under a different account than before.
- **Sending is strictly `deps`-injected, never called directly from the pure logic** — `executarVerificacaoLembretes_` only ever calls `deps.pushTokens.list()`/`deps.push.enviar(...)`/`deps.whatsapp.enviar(...)`, each guarded by `if (deps.pushTokens && deps.push)` / `if (deps.whatsapp)`. This is the exact same testability pattern `verifyGoogleToken_` already established (a function that calls real `UrlFetchApp`/`PropertiesService`/`Utilities` directly is fine to exist at the top level, as long as the *tested* logic only ever reaches it through a `deps.X` field a test can omit or mock) — it is why the entire existing 407-case suite kept passing unchanged the moment these two features were wired in: every other test's `makeDeps` simply doesn't set `pushTokens`/`push`/`whatsapp`, so the guards make both new channels silent no-ops exactly as before.
  - `enviarPushFCM_` returns `true` (sent), `false` (the token is dead — FCM said `UNREGISTERED`/`NOT_FOUND`/`INVALID_ARGUMENT`, e.g. the app was uninstalled or notification permission revoked), or `null` (not configured, or a transient failure) — only `false` triggers `deps.pushTokens.remove(token)`, so a dead registration stops being retried forever but a mere hiccup doesn't lose it.

The steps below are for **direct mode**: (1) if the Google Cloud OAuth consent screen is in *Testing* status, add their email under **Test users** (Google Cloud Console → Google Auth Platform → Audience) — otherwise Google itself blocks the login; (2) share that company's Google Sheet with their account in Drive (Editor to enter data, Viewer to only read); (3) as that company's Master, add them in **Ajustes → Adicionar usuário** inside the running app. At sign-in `resolveCompaniesForEmail` (`js/app.js`) finds their companies by checking every known company's `Usuários` tab (`isEmailListedInCompany` in `js/usuarios.js`, companies from `allKnownCompanies()` in `js/tenants.js`), so step 3 alone routes them; `js/tenants.js` per-email entries now only matter for the owner's own accounts and for adding a brand-new *company*. Drive sharing (step 2) cannot be automated from this app without asking the Master for the full `drive` OAuth scope (broad access to their whole Drive) — that was deliberately not done; the add-user form tells the Master to share the sheet instead. Missing any step leaves that person unable to get in (fails closed).

### File layout

- `index.html` — two top-level views: `#login-screen` (shown first) and `#app-shell` (sidebar + main content, shown after auth). Only one is visible at a time (`hidden` attribute toggled in `js/app.js`).
- `css/style.css` — all styling, including the login screen, the sidebar layout, and the chart color tokens (light/dark) from the dataviz skill's reference palette.
- `js/config.js` — `CLIENT_ID`, `SPREADSHEET_ID`, sheet name, and OAuth scopes. Not meant to hold real secrets in a shared repo.
- `js/auth.js` — Google Identity Services token client (OAuth in-browser, no backend). Also persists the access token to `sessionStorage` (`saveTokenToSession` / `loadValidTokenFromSession` / `clearTokenSession`) so a page reload in the same tab resumes the session without a new login prompt; closing the tab clears it (that's `sessionStorage`'s native behavior, not custom logic). `signOut()` clears it and revokes the token.
- `js/sheets.js` — thin wrapper around the Sheets API: `fetchSheetValues` (`values.get`, supports `valueRenderOption`) and `updateSheetRow` (`values.update` / PUT on one specific `A{row}:J{row}`-style range, always `valueInputOption=RAW` — see note below).
- `js/lancamentos.js` — fetches and parses the **Lançamento** tab (`fetchLancamentos`); reads with `UNFORMATTED_VALUE` so dates come back as serial numbers (converted via `sheetSerialToDate`) instead of locale-formatted strings. `dateInputToSheetSerial` is the inverse, used when writing a new row. `findNextLancamentoRow` scans column A to find the true next empty row (see note below). `stripCode` strips the leading `"N - "` prefix used throughout the lookup tabs.
- `js/lookups.js` — fetches the small lookup tabs (Lojas, Contas, Empresas, Categoria, Pessoa) that back the lançamento form's dropdowns. Every lookup tab's column C ("Complemento") holds the exact `"N - Nome"` string that `Lançamento`'s own columns store — `toLookupOption` reads that column directly so form submissions stay byte-identical to existing data. `Categoria` is additionally filtered to `Status === "Ativo"`.
- `js/dashboard-data.js` — pure aggregation functions over parsed records: `filterByDateRange`, `computeKpis`, `computeByLoja`, `computeByCategoria`, `computeByMonth`, `topNWithOthers`.
- `js/charts.js` — hand-rolled inline-SVG chart renderers (diverging bar, ranked bar, grouped monthly bar, donut) plus shared tooltip/legend/table-toggle helpers. No charting library dependency, per the vanilla-JS constraint.
- `js/dashboard.js` — wires the date filter (with presets: mês atual/anterior, ano atual, tudo) to the aggregation + chart functions and renders the KPI tiles. `initDashboard` does the first load (sets up filter handlers, defaults to "mês atual"); `updateLancamentos` refreshes the underlying data and re-renders *without* resetting the user's current filter — used after a form submission.
- `js/form.js` — the "Novo lançamento" form: populates the lookup dropdowns, validates, flips the sign of `Valor` based on `Tipo` (Saída is stored negative, matching existing rows), computes the target row via `findNextLancamentoRow`, writes it via `updateSheetRow`, then calls `refreshLancamentosAndDashboard`.
- **One-time setup functions must guard against re-invocation** (`if (xInitialized) return; xInitialized = true;`) — anything wired up inside `selectCompanyAndLoadApp` can run more than once per page load (log out and back in, or pick a different company, without a full page reload), and `addEventListener` doesn't replace a prior listener on the same element, it stacks another one. `setupNavigation`, `setupLancamentoForm`, and `setupEstoqueForm` all follow this; found the hard way when `setupNavigation` didn't and a second login made every submenu toggle button open-then-immediately-close on click (two stacked listeners flipping `hidden` twice per click). If you add a new one-time setup function called from `selectCompanyAndLoadApp`, give it the same guard.
- **Sidebar collapse**: `#sidebar-collapse-btn` toggles `.sidebar.collapsed` — per explicit user request, collapsed means *only* that button stays visible (nav and the user/Sair footer are `display: none`, not shrunk to icons), persisted per-browser in `localStorage` (`financegold_sidebar_collapsed`) via `loadSidebarCollapsedPref`/`saveSidebarCollapsedPref` in `js/nav.js`. There's no way to switch views while collapsed by design — expand first. (An earlier icon-rail-with-flyout-submenu version was built and then deliberately stripped back down to this simpler behavior — don't reintroduce icon spans or a flyout panel unless asked again.)
- **`.sidebar-nav` has no `flex: 1`** — it used to stretch to fill the sidebar's full height, which pinned the footer to the bottom of the viewport and left a large empty gap below just 2-3 nav items. It's sized to its content instead, so the sidebar stays compact with few items and simply grows as more are added — don't re-add `flex: 1` there without re-introducing that gap.
- `js/nav.js` — sidebar view switching (`.nav-item` click ↔ `.view-section` show/hide + topbar title). Add a new view by adding a `.nav-item[data-view=...]` button, a `.view-section[data-view=...]` section, and a title in `VIEW_TITLES`.
- `js/app.js` — orchestrates auth, the two top-level screens (`#login-screen` / `#app-shell`), and kicks off the initial data + lookups fetch on sign-in.

**Why the form doesn't use `values:append`:** the `Lançamento` sheet's dimensions extend to row ~2531 (formatting) even though real data ends around row ~1571, and `values:append`'s "detect the table" heuristic used that whole formatted extent as "the table," landing new rows far past the real data instead of right after it — confirmed by testing. `findNextLancamentoRow` + `updateSheetRow` (a targeted `values.update` PUT) replace that with a deterministic write to the exact next row.

**Why `updateSheetRow` uses `RAW` instead of `USER_ENTERED`:** the sheet stores `Data` as a numeric date serial (see `Lançamento` sheet), and `USER_ENTERED` would depend on Sheets correctly guessing the date format of a plain string, which is locale-dependent and unverified from this codebase. Writing the already-converted serial number via `RAW` matches the existing column's actual representation exactly, so new rows read back identically to old ones. If a future field needs formula evaluation, that field alone would need `USER_ENTERED` (a per-request setting, not per-cell) — reconsider then.

**Known limitation:** `findNextLancamentoRow` + `updateSheetRow` is not atomic — two people saving a lançamento at the same moment could compute the same target row and overwrite each other. Fine for now (single-user usage); revisit if the app gets concurrent users.

### Estoque module

- `js/estoque.js` — data layer for the **Estoque** tab (16 columns, A:P — see the header list in that file's top comment). `fetchEstoque` parses every row (each carries `.linha`, its sheet row number, and `.raw`, the original 16-value array — writes always start from a copy of `.raw` with specific indices patched, never reconstructed field-by-field, so a partial update can't accidentally blank out an unrelated column). `findNextEstoqueRow` + a targeted `updateSheetRow` write are used for `createEstoqueItem`, for the same table-detection-heuristic reason documented above for Lançamento.
- **Custody tracking ("com vendedor") uses the existing `Observação` column, not a new one** — this was an explicit user decision (they declined adding a new column to the live sheet). Convention: notes are appended to whatever's already in `Observação`, separated by `" / "` (see `appendObservacao`). The *current* custody state is read from the **last** `" / "`-separated segment only (`parseCustodyFromObservacao` / `computeEstoqueStatus`), matching against `"Com vendedor: <nome>"`; anything else in that last segment (including a fresh `"Retornou à loja"` note) means the piece is back in the store. Don't change this parsing to scan the whole string — only the trailing segment reflects the current state, by design (older notes stay as history).
- **Column convention differs by field**, confirmed against the real sheet data — don't assume every column matches Lançamento's style: `Produto`/`Tipo`/`Marca` store the `"N - Nome"` complemento form (same as their lookup tabs' column C), but `Loja`/`Comprador`/`Vendedor` store the **plain name** (column B of `Lojas`/`Pessoa`, exposed as `lojasPlain`/`pessoasPlain` in `js/lookups.js`) — unlike Lançamento's `Loja`/`Pessoa` columns, which use the complemento form. Mixing these up would silently write data in a format inconsistent with the rest of that column.
- `js/export.js` — `downloadCsv(filename, headers, rows)`, a small dependency-free CSV export (Blob + a throwaway `<a download>`, UTF-8 BOM so accented characters render right in Excel). Both list views export whatever is currently filtered/sorted on screen, not the whole dataset: `exportEstoqueCsv` in `js/estoque-ui.js` and `exportLancamentosCsv` in `js/lancamento-lista.js`. Deliberately CSV, not a real `.xlsx` — that needs a library, and CSV opens natively in Excel/Sheets with zero new dependencies, consistent with the vanilla-JS constraint.
- `js/estoque-ui.js` — the "Consultar estoque" list (filters: loja, status, tipo, free-text search), the sold/custody/return actions (inline panels, not native `prompt()`/modals — `showCustodyPanel` / `showSoldPanel` / `handleReturnToStore`), and the "Nova peça" form.
- **Drag-and-drop reordering is local-only** (another explicit user requirement: don't touch the sheet's row order). `estoque-ui.js` persists the dragged order as an array of `linha` numbers to `localStorage` (`financegold_estoque_order`) and `applyEstoqueOrder` re-sorts by that on every render; it's per-browser, not synced, and items not in a saved order fall back to sheet order at the end.
- **Row numbers ("número de lançamento")**: both `js/lancamentos.js`'s `parseLancamentoRow` and `js/estoque.js`'s `parseEstoqueRow` attach `.linha` (the real sheet row) to every parsed record — requested by the user for both modules. Shown per-card (`#<linha>`) in both the Estoque and (since 2026-10-16) Fluxo de Caixa lists, since both are now per-item card views; also still shown in the "Novo lançamento" form's save confirmation ("Lançamento salvo na linha X").
- **"Fluxo de Caixa" became cards, not a literal spreadsheet table (2026-10-16)**: reported as reading like "um reflexo literal dos itens da planilha base, inclusive células, colunas vazias" — the old view was a real `<table>` with one `<th>`/`<td>` per sheet column (Loja, Conta, Empresa, Categoria, Tipo, Peso, Pessoa, Observação, plus any extra adaptive-schema columns), including ones blank on every row for a given company's sheet (the old `colunasSemDados` helper hid a whole *column* only when **every** row's cell was empty, which still left plenty of per-row blank cells visible as empty `<td>`s). Asked for explicitly: keep showing the sheet's real text, just presented "mais integrada ao sistema como acontece na aba Estoque" — the Estoque module's own card look. `js/lancamento-lista.js`'s `buildLancamentoCard` now builds one `.fornecedor-card` per row (reused directly, not re-cloned — same precedent as Contas a Pagar/Receber reusing Fornecedores' classes, see above) with a title line (date + categoria), a meta line that **only ever joins the fields that record actually has** (`[loja, conta, empresa, pessoa, peso].filter(Boolean).join(" · ")` — a blank field just isn't in the string, never an empty cell), an extras line for the sheet's own adaptive columns (same pattern Estoque already uses for its extras), an observação line, and the valor as a colored pill (`.lanc-valor-entrada`/`.lanc-valor-saida`, green/red, reusing `.fornecedor-status`'s pill shape) instead of a table cell. **Explicitly scoped to display only** — `js/lancamentos.js` (fetch/parse) and `js/form.js` ("Novo lançamento", the write path) are completely untouched, per the user's own "lembre de manter o padrão de alimentação da planilha"; CSV export (`exportLancamentosCsv`) also untouched, since a flat column export is the right shape for a CSV regardless of how the screen displays it. The old `#lancamento-lista-table`/`.lanc-col-*` CSS (a separate "table visually collapses into a stacked grid below 860px" mobile-only hack, see the Mobile layout note above) is gone along with the table markup — real cards need no separate mobile code path, they're already cards at every width. **A real mobile bug found and fixed while verifying, not assumed away**: `.fornecedor-card`'s `justify-content: space-between` with no `flex-wrap` let a wide BRL value pill overflow off-screen at phone widths — Fornecedores/Contas never hit this because "Ativo"/"Pendente" are short, but a value like "R$ 1.850" is wide enough to trigger it. Fixed with the same `flex-wrap: wrap` + `.fornecedor-status { margin-left: auto }` pair `.estoque-card` already uses for its own badge-overflow case, added as `.fornecedor-card`/`.fornecedor-status` rules in the same `≤860px` media block — this also incidentally fixes the same latent risk for Fornecedores/Contas if either ever gets a longer badge. **Verified in headless Chrome**, including the real-viewport gotcha documented under Visual design system (a plain `--window-size=400` silently lays out at Chrome headless's ~500px floor; used the documented same-origin-iframe workaround to get a true 400px render) — confirmed no horizontal overflow and the value pill wraps correctly below the title on a real phone-width render, both before-vs-after the flex-wrap fix. `sw.js` bumped to `v83`.

Not yet built: views for the other tabs (Contas, Categoria, Pessoa, etc. — these mostly just back dropdowns for now, not their own screens).

## Working conventions

- Treat the Google Sheet as the source of truth for financial/inventory data; do not alter values or the local `.xlsx` reference copy.
- Match new sheet-writing code to the existing column layout/order per tab rather than inventing a new schema, unless the user asks for a structural change.
- Keep OAuth Client ID / Spreadsheet ID out of source in a way the user can supply locally (e.g. a small untracked config), rather than hardcoding secrets into committed files.
